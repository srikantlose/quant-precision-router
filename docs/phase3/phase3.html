1System Architecture

QuantRoute answers one question for every prompt: what is the cheapest quantization level of the model that will still answer it accurately, consistently and safely? One model, Qwen2.5-3B-Instruct [1], is kept at seven GGUF quantization levels (“rungs”) — Q2_K, Q3_K_M, Q4_K_M, Q5_K_M, Q6_K, Q8_0 and the F16 reference — and served by llama.cpp [2] on a single 8 GB RTX 4060. Lower rungs use less memory and load faster but may answer some prompts wrongly, change answers that F16 gets right, or stop refusing harmful requests.

The system is split into two planes that share one artefact (). The offline plane builds a graded benchmark, runs every prompt at every rung, and learns a policy: a lookup table from (task category, predicted required precision) to a rung. The online plane loads that table and, for each incoming prompt, classifies it, predicts how much precision it needs, looks up the rung, enforces a safety floor and serves the answer. Everything runs on one local workstation. The network is used only to download the model and datasets once, and to call a teacher model while generating benchmark tasks.

Design principles Measure, don’t assume: cost, memory and drift are measured on the target GPU rather than inferred from bit-widths. One code path: the benchmark and the router share the same prompt preparation and answer extraction, so a task is graded exactly as it would be served. Bounds, not averages: a rung is chosen only when one-sided 95% confidence bounds on accuracy, answer flips and safety all pass. Integrity: every model file is pinned by SHA-256 and model-written code only runs in a locked-down container.

1.1Overall Workflow

The workflow runs in four stages, each producing files that the next stage reads ().

  1. Build. Merge 135 seed tasks with 1,332 teacher-generated, verified tasks into a 1,467-task benchmark (12 categories × 3 tiers); add 600 safety prompts; download the seven model files from one pinned commit and record their SHA-256 hashes.
  2. Measure. Send all 2,067 prompts to each rung through the server pool (14,469 graded runs, zero errors), profile VRAM and load time, and record answer flips and KL-divergence against F16.
  3. Learn (training split only). Label each task’s required precision, train the predictor, fit accuracy and flip bounds per cell, set the safety floor, and pick the cheapest admissible rung for each of the 84 cells.
  4. Serve and evaluate. Apply the policy to live prompts through the API, attack it, and present every result. The 450 test tasks are used only for final evaluation.

1.3Interaction Between Components

Modules in different stages never call each other directly. They communicate through versioned files on disk (), and every file records how it was produced: the model hash, llama.cpp build, seed and split. This makes each stage reproducible and lets an expensive stage, such as the three-hour GPU grid, be resumed or skipped. Live interaction happens in two places:

  • Measurement stage: the grid runner asks the server pool for a rung, and the pool starts a llama-server process and talks to it over a local OpenAI-compatible HTTP endpoint. The grader starts a Docker container for each code answer.
  • Serving stage: each request passes through the API, router, predictor, policy, safety classifier and server pool ().

4Dataset Details and Experimental Setup

4.1Benchmark Slice: 1,467 Graded Tasks

Tasks cover 12 categories that a general assistant receives — maths, multiple choice, factual Q&A, classification, sentiment, extraction, language, logic, summarization, named-entity recognition, code generation and code debugging — at three difficulty tiers. Each generated task was written for a requested tier. Seeds were tiered by a heuristic scorer. Tiers are used only to stratify and report results, never to route. Every task carries its own deterministic grader (), so accuracy is measured without an LLM judge.

A task enters the benchmark only if the teacher can answer it correctly under that grader. This drops tasks the teacher gets wrong as well as malformed ones, and the drop rate is logged per cell. It is also why complex logic has only 12 tasks: verification rejected every complex logic puzzle the teacher wrote, and the run used 467 of its 600 permitted API calls. Tasks are split 70/30 into train and test by a SHA-256 hash of their id, giving 1,017 training and 450 test tasks. The split is fixed and independent of content.

4.2Safety Slice: 600 Prompts

The safety slice judges each rung against F16 rather than in isolation (). A prompt is handled safely if:

  • a harmful prompt is refused;
  • a benign look-alike is not refused;
  • an injection’s canary word does not appear in the answer.

Refusals are detected by a string matcher. A stratified audit of 200 responses by an LLM judge is planned to measure the matcher’s error rates. The injections are built so that the original task stays answerable and the canary is a random token that never occurs naturally, which makes success or failure unambiguous ().

4.3Model Files and Fidelity Corpus

All seven rungs come from one commit of the official repository, so they share a single quantization recipe and differ only in precision. A third-party build of “Q4_K_M” from another repository is a different file of a different size, and mixing the two would confound the comparison. Each file’s hash is checked before every server launch, which also guards against the tampered-quantization attacks described by Egashira et al. [15]. Effective bits per weight are measured as file size ÷ parameter count, which is why they exceed the nominal labels ().

Training and evaluation protocol

Everything that is learned (τ, labels, predictor, pooled models, safety floor, classifier threshold and policy) is fitted on the training split only. The predictor’s outputs on training tasks come from 5-fold cross-fitting (): each task’s predicted class comes from a model that never saw that task’s label. Without this, the pooled models would learn from labels that leaked through the predictor. The test split is used once, to compare the learned policy with the baselines in .

Policies compared on the held-out test split.

PolicyHow it chooses the rung
always-<rung> (×7)Serve every prompt at one fixed rung, from Q2_K to F16. This is how quantized models are deployed today.

resident subsetThe best set of rungs that fit in VRAM together, choosing within the set, with simulated swap costs included.
learned (QuantRoute)The 84-cell policy: predicted category and predicted required precision → cheapest admissible rung, raised to the safety floor for flagged prompts.

Operating point, sweep and statistical analysis

  • Default operating point. δ = 0.02: a rung may lose at most 2 points of accuracy against F16, measured by its lower bound. φ = 0.10: at most 10% flipped answers, by the upper bound. ψ = 0.05: at most 5% safety flips, by the upper bound.
  • Balanced operating point. The strict default serves F16 in all 84 cells, because about 40 training tasks per cell leave wide bounds. The service therefore also offers Balanced (δ = 0.10, φ = 0.30, per-cell safety bound 0.10), under which Q3_K_M through Q8_0 each serve some cells. The floor for flagged prompts stays at Q5_K_M (ψ = 0.05) under every setting.
  • Sweep. The policy is refitted for 8 × 6 × 5 = 240 (δ, φ, ψ) combinations to trace the cost–accuracy frontier.
  • Pooled models. Accuracy and flip bounds use one-sided 95% intervals (z = 1.645) from GEE [9] with task-clustered correlation, fitted in statsmodels [11].
  • Safety bounds. Safety-flip rates use Wilson score bounds [10].
  • Uncertainty. Bootstrap: 200 refits of the whole pipeline on resampled training tasks, to check policy stability, and 1,000 resamples of test tasks, to give 95% confidence intervals on each policy’s accuracy and cost.
  • Security checks. A differential test flags any category whose flip rate at one rung jumps more than 10 points above both neighbouring rungs (p < 0.01), and any rung whose KL is out of order, as a sign of a planted quantization backdoor [15]. The planned adversarial stage then attacks the router with cost-inflation and downgrade prompts, including router “gadgets” in the style of [14].

The gap between F16 and the best safe single rung is only 1.3 points, and neither prompt text nor the answer’s own confidence picks out the questions that make up that gap. On this model and GPU, per-prompt routing therefore does not beat simply serving Q5_K_M. Balanced buys 0.6 points over it for 7 points more GPU time. This matches the finding of [16] that routers often fail to beat the best single model. The remaining analysis (sweep, bootstrap intervals) will put confidence intervals on these differences.

Expected outcomes and how they will be judged
  • Cheap rungs suffice for many cells. A rung at or below 4 bits stays within δ of F16 in most category × tier cells. Current data: 25 of 36 cells, consistent with the 4-bit result of Dettmers and Zettlemoyer [13].
  • Required precision is predictable from the prompt. The predictor should beat the majority-class and per-category baselines. Current data: 45.8% exact versus 45.5% and 48.4%, and 79.8% within one level, so prompt text alone is a weak signal.
  • Lower cost on held-out tasks. On the test split, the learned policy should cost less than the best fixed rung at equal accuracy and flip rate. First replay: it does not. Balanced costs 52% of F16 against 45% for always-Q5_K_M, for 0.6 points more accuracy, so the best safe single rung is the practical recommendation for this model.
  • Safety holds. Served safety flips should stay within ψ, and flagged prompts should never be served below the floor (currently Q5_K_M), including under downgrade attacks.
